## 不能改错的核心口径

### 1. 公会的主体与关系

- 公会、用户、主播、成员、公会长、管理员、运营、财务、ACM 和 BD 是不同主体或角色。一个账号可承担多个角色，但不能因此合并其权限、数据范围或结算归属。
- 建会有两种不同结果：用户主动申请须经审核；运营发起建会在用户接受前只是待确认邀请，不代表公会已创建。
- 加入、邀请、绑定和成员迁移必须校验同一运营大区、账号状态、冲突关系、频率限制与当前最终状态；并发申请或邀请不能让用户同时加入多个公会。
- 公会长可管理本公会管理员及其细分授权；管理员只能在已授予的范围内操作。邀请成员、查看成员数据和修改公会资料是可拆分的权限。
- 冻结、恢复、删除、强制删除、成员移出、主动离会、转区和管理员变更是不同动作。当前关系变化不能删除或回写已发生的历史业绩、工资、结算、排名和荣誉。

### 2. 与 ACM/BD 的交叉边界

- 公会是独立经营与用户关系域；ACM V3 是外部拓展团队的组织、模板、权限、额度、团队树和公会直接归属治理体系。
- BD 通常是 ACM 团队中承担公会拓展职责的成员或层级，不等于独立的旧 BD 产品，也不天然等于公会长、运营负责人或工资归属人。
- 同一统计周期内，公会应有唯一有效的直接归属人，并处于可解释的团队路径。创建/转移公会时，需要同时校验 ACM 权限、团队额度、模板关系、目标大区、现有归属与提交时状态。
- 不能因 ACM 具备团队/后台能力，就把公会用户端权限、数据可见、报表可见或工资归属一并放开；必须分别判断功能权限、用户端数据范围、后台管理范围与报表范围。
- ACM 团队迁移、账号停用、模板和权限调整可能影响当前周期可见范围和归属，应先做影响预览并核对团队树、公会列表、权限/额度和操作记录；历史冻结结果不得用当前团队树重算。

### 3. 数据、周期与快照

- 所有业务日、周期边界、筛选、结算和运营操作以页面标注的 UTC+3 为准。页面中的当前周期通常可刷新或为预估，历史周期必须使用当期冻结关系、结果和配置版本。
- 当前基础资料（昵称、头像、当前成员数）可能在历史页面中继续显示；这不意味着历史归属、业绩、工资、等级、名次或荣誉可被当前资料反向改写。
- 看板与报表必须明确对象、指标单位、业务线/大区、周期、角色、数据范围、当前/历史状态和汇总/明细层级。查询、汇总和导出应共享同一筛选口径。
- 导出是生成时点的离线副本，必须可识别大区、报表类型、周期、筛选和生成时间；异步导出需要查看下载任务状态，不能连续重复提交。
- 同一大区有数据不代表适用全部列、工资、等级、最强公会或 PK。缺列可能代表不适用，不能导出后私自补列或套用其他区域公式。

### 4. 业绩、工资与资金

- 先确定大区、周期、对象关系、统计模式、当期配置和历史/当前状态，再解释“业绩”“工资”“余额”或“排名”。同名指标在不同大区和政策中可能有不同来源和公式。
- 结算顺序应是：确认周期与数据完整性 -> 确认有效归属和配置 -> 聚合与计算 -> 勾稽 -> 正式发布/发放 -> 保护成功对象并处理失败对象。
- 当前预估不能直接作为正式发放清单。部分失败时只能修复并补跑失败对象，绝不能把已成功的资金动作整体重复发起。
- 工资、预支、借支、历史欠款、余额、佣金、提现账户和主播转入账户应分字段、分责任主体、分生效范围展示和审核；不能用一个总额掩盖负债或资金状态。
- 充值数据、礼物业绩、工资结算和奖励是不同业务域。涉及幸运礼物、自赠、钻石/红钻/宝石折算、佣金或 TG/BD/BDM 结算时，必须按目标大区当期政策另行核对。

### 5. 等级、榜单、荣誉与活动

- 业绩等级、等级资源、铭牌和荣誉是独立状态。等级正确而资源为空是配置/素材问题；铭牌可能有独立有效期；荣誉是历史事实，不能以当前等级、名称或成员关系替代。
- 当前榜单、周期评级和历史荣誉的产生时点不同。隐藏其他公会业绩只影响展示，不影响真实排名；历史名次、等级和荣誉以当期结果保留。
- 最强公会或其他榜单活动应分别校验榜单、等级、荣誉资源、奖励包、发放状态、目标大区配置及幂等性。榜单有结果不代表荣誉和奖励一定成功。
- PK 需按赛事、报名、赛段、对阵、成绩、晋级和结束状态顺序处理。调整赛段、提交分数或处理晋级会改变后续结果，必须留证并核对影响。

### 6. 运营后台与高风险动作

- 后台菜单权限和数据范围是两层控制；看得到菜单或按钮不等于可处理所有大区、公会或团队。不得通过共享账号或代操作绕过权限。
- 高风险动作遵循：确认环境、账号、大区、对象、周期和当前值 -> 记录影响与生效时间 -> 预览 -> 提交时再次校验 -> 核对最终业务状态、关联关系、报表与操作记录。
- 当前配置、未来配置、历史发布版本和已参与结算的配置必须分开。周期敏感配置应在合法周期边界生效；已生效结果需通过修正版本和补偿处理，不能简单取消或覆盖。
- 发现重复成功资金记录、配置版本无法确认、历史快照变更、关系状态不一致、持续报表差异或自动任务重复失败时，应停止重复操作，保留筛选、对象、周期、时间和操作证据，升级技术与财务/运营联合处理。

## 需求评审默认顺序

1. 明确目标业务线与运营大区，是否涉及转区、跨区或旧版本兼容。
2. 明确目标入口：用户端、公会后台、运营后台、看板、报表/导出、结算、活动，或 ACM/BD 团队治理。
3. 明确目标角色与四类权限：功能、用户端数据、后台管理、报表数据。
4. 明确对象关系：公会、用户/主播、成员、公会长、管理员、直接归属人、ACM/BD 团队及其有效状态。
5. 明确时间与配置：UTC+3 周期边界、当前预估/正式结果/历史冻结、统计模式、政策版本与生效时间。
6. 明确跨入口一致性：用户端、后台、看板、报表、导出、任务与结算是否读取同一权威结果，是否会重复出数或破坏快照。
7. 补齐异常与验收：权限不足、无数据/不适用、重复提交、并发、超时、部分成功、配置变更、资金保护、审计、通知和回滚/受控修复。

## 主动提醒清单

- 需求未写大区、周期或当前/历史状态时，提醒先补齐这些前提，避免套用默认区或当前数据误解历史。
- 需求把“能看”“能操作”“后台能搜到”“能导出/看报表”视为同一个权限时，拆成四类权限与最小数据范围。
- 需求要求按当前公会/成员/ACM 团队关系回算历史工资、归属、排名或荣誉时，提醒历史冻结快照不得直接回写。
- 需求跨区复用工资、等级门槛、看板列、活动、奖励或周期时，提醒确认目标区统计链路和当期有效配置；“不适用”不等于 0。
- 需求涉及建会、入会、邀请、转移、冻结或删除但只设计成功态时，补齐待审核、待确认、拒绝、过期、冲突、频率限制、并发、部分成功、通知和历史保留。
- 需求涉及结算、预支、欠款、佣金、提现、奖励或补跑时，提醒资金幂等、成功对象保护、审批依据、勾稽、可审计性和受控修复路径。
- 需求新增看板/导出时，补充指标定义、单位、状态、筛选、动态列、权限、生成时间、汇总与明细勾稽，以及数据延迟/空值/不适用表现。
- 需求改 ACM/BD 的模板、额度、成员树或公会归属时，提醒影响预览、提交二次校验、操作审计和用户端/后台/报表三方核对。
- 需求涉及等级、荣誉、榜单、奖励或 PK 时，分别检查配置、资源、周期结果、任务幂等和人工操作是否与自动处理冲突。

## 历史版本注意事项

- V1/V2、旧 BD、旧报表和旧入口只承担历史追溯或约定期限内的兼容，不作为当前业务权威口径。
- 公会转区影响后续适用规则，不自动搬迁或改写历史数据；历史周期仍按原大区、原归属和原配置解释。
- 删除、成员移出、离会、冻结/恢复和团队迁移不能用于清理历史工资、结算、榜单、荣誉或操作记录。
- 来源文档保留的旧知识库编号链接不是仓库内真实路径；下次任务以 PROJECT_INDEX 的当前文件为准。
