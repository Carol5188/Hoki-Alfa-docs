# 用户端与成员管理

最后核验日期：2026-08-19

## 适用人群

面向处理建会、入会、邀请、审批、成员权限、退出和用户投诉的产品与运营人员。

## 功能说明

用户端公会能力围绕三件事展开：找到并了解公会、建立或加入关系、在权限范围内管理成员。不同角色看到的按钮不同，运营排查时要同时核对用户角色、公会状态、运营大区和当前客户端版本。

## 公会搜索与主页

### 搜索公会

用户可以通过公会标识或可识别的公会信息查找目标公会。搜索结果通常包含公会名称、头像、介绍、成员或管理者信息，以及最新荣誉等公开信息。
| 适用角色 | 前置条件 | 操作结果 | 常见失败原因 |
| --- | --- | --- | --- |
| 登录用户 | 目标公会存在且可查询 | 进入公会详情或主页 | 公会不存在、被冻结或查询内容无匹配 |

### 公会主页

公会主页用于展示：

+ 公会基础资料和介绍。
+ 公会长与管理员。
+ 当前成员和在线信息。
+ 当前周期业绩与下一等级目标。
+ 当前等级对应的头像框、背景或徽章资源。
+ 最新荣誉、公会公告和是否有待处理消息。
  主页展示的是当前状态，不应当作历史结算凭证。当前业绩和等级可能随数据刷新继续变化。
  
  ### 修改资料、公告和设置
  
  | 功能                                                                 | 谁可以操作                 | 主要限制           | 生效结果              |
  | ------------------------------------------------------------------ | --------------------- | -------------- | ----------------- |
  | 修改公会资料                                                             | 公会长；有修改资料权限的管理员可操作允许项 | 公会必须正常，内容需通过校验 | 更新公会对外资料          |
  | 修改公告                                                               | 公会长                   | 冻结时不可修改        | 主页展示新公告           |
  | 排名数据展示设置                                                           | 公会长                   | 仅管理自己公会        | 控制普通查看者能否看到榜单具体业绩 |
  | 关闭排名数据展示后，榜单名次和成员信息仍可能展示，但普通查看者只能看到自己的业绩，其他人的具体数值会被隐藏。公会长仍可查看完整数值。 |                       |                |                   |
  
  ## 建会流程
  
  ### 用户主动申请
1. 用户填写公会名称、头像、介绍、联系方式、国家、证明材料和加入密码等资料。
2. 系统校验是否存在有效申请，避免重复提交。
3. 平台运营在建会审核中查看并处理申请。
4. 审核通过后建立公会和公会长关系；审核拒绝则保留处理结果供追溯。
   
   | 适用角色  | 前置条件       | 操作结果    | 常见失败原因             |
   | ----- | ---------- | ------- | ------------------ |
   | 无公会用户 | 没有冲突中的建会申请 | 生成待审核申请 | 重复申请、资料不完整、用户状态不允许 |
   
   ### 运营发起、用户确认
5. 运营选择目标用户并填写公会资料，创建待用户确认的申请。
6. 用户在有效期内查看申请详情。
7. 用户选择接受或拒绝。
8. 接受后创建公会；拒绝或过期后不创建。
   该流程用于运营已确认合作对象、但仍需要用户本人确认的场景。运营不能把“已发送邀请”当作“公会已创建”。
   
   ## 加入公会
   
   ### 申请加入
   
   用户找到目标公会后，输入公会密码并选择适用的加入时长。系统会校验用户与公会是否同一运营大区。
   
   | 场景                                            | 处理方式           |
   | --------------------------------------------- | -------------- |
   | TR、CIS                                        | 密码和其他条件通过后直接加入 |
   | 其他支持申请的大区                                     | 生成待公会管理者审批的申请  |
   | 申请记录可能处于待处理、已同意或已拒绝状态。公会长或管理员处理后，系统向用户发送相应通知。 |                |
   | 常见失败原因：                                       |                |
+ 用户与公会不在同一运营大区。
+ 公会密码错误。
+ 用户已有公会或当前状态不可加入。
+ 用户短时间内重复申请，触发频率限制。
+ 公会不存在、冻结或不再接受加入。
  
  ### 公会邀请
  
  公会长或有邀请权限的管理员可以精确搜索候选用户。搜索支持用户标识和靓号的等值匹配，不是模糊搜索。
  标准流程：
1. 搜索候选用户。
2. 查看用户是否已有公会、是否有待处理邀请或加入申请。
3. 选择后台当前允许的加入时长。
4. 发送邀请。
5. 用户在邀请列表中接受或拒绝。
6. 接受成功后建立成员关系，并消费本次有效邀请。
   
   | 前置条件                                                         | 说明                    |
   | ------------------------------------------------------------ | --------------------- |
   | 操作者权限                                                        | 公会长，或拥有邀请成员权限的管理员     |
   | 同区                                                           | 候选用户和公会必须属于同一运营大区     |
   | 用户状态                                                         | 候选用户不能处于不允许加入的公会状态    |
   | 频率限制                                                         | 同一公会对同一用户的重复邀请会受到时间限制 |
   | 加入时长                                                         | 只能选择当前大区配置的有效选项       |
   | 邀请搜索没有结果时，不一定是用户不存在，也可能是无权限、跨区或目标用户不可邀请。运营应按顺序排查，不应要求用户反复尝试。 |                       |
   
   ## 成员列表与身份
   
   公会成员分为公会长、管理员和普通成员。成员列表通常优先展示公会长与管理员，再展示其他成员；新页面支持分页，旧页面可能一次返回全部成员。
   
   ### 设置或取消管理员
   
   公会长可以把当前公会成员设为管理员，或取消管理员身份。成为管理员后，系统为其建立默认授权；公会长可再调整细分权限。
   
   | 操作                                      | 前置条件                | 操作结果                |
   | --------------------------------------- | ------------------- | ------------------- |
   | 设置管理员                                   | 目标用户属于当前公会，操作者是公会长  | 目标用户获得管理员身份及默认权限    |
   | 调整权限                                    | 操作者是公会长，目标用户是本公会管理员 | 更新查看数据、修改资料、邀请成员的组合 |
   | 取消管理员                                   | 目标用户是本公会管理员         | 管理员身份和管理授权失效，成员关系保留 |
   | 公会长不能把自己的最高管理身份改成普通管理员权限，也不能操作其他公会的管理员。 |                     |                     |
   
   ## 加入申请审批
   
   公会长和符合页面授权条件的管理者可以查看近期申请。待处理申请会触发公会新消息提示。
   
   | 处理结果                                                       | 对成员关系的影响            | 通知       |
   | ---------------------------------------------------------- | ------------------- | -------- |
   | 同意                                                         | 用户加入公会，采用申请时确认的加入时长 | 通知申请人通过  |
   | 拒绝                                                         | 不建立成员关系             | 通知申请人被拒绝 |
   | 审批前应再次确认用户状态，因为用户可能在申请后已加入其他公会或发生大区变化。并发状态冲突时，以系统最终校验结果为准。 |                     |          |
   
   ## 踢出成员与主动离会
   
   ### 踢出成员
   
   踢人页面会先展示当前是否可踢和相关限制。执行者必须具备管理资格，目标必须是可被移除的本公会成员。
   成功后：
+ 目标用户离开公会。
+ 相关关系和缓存更新。
+ 目标用户及公会管理者收到通知。
+ 已结束周期的历史数据不被删除。
  
  ### 主动离会
  
  普通成员可以主动离开公会，但必须满足离会冷却规则。页面应先显示距离可离会还剩多少天；未到期时提交会被拒绝。
  离会成功后，不会自动取消用户在历史周期中已经形成的业绩、工资或结算记录。
  
  ## 消息与通知
  
  公会相关消息包括：
+ 邀请到达、接受或拒绝。
+ 加入申请通过或拒绝。
+ 成员主动离会或被踢出。
+ 公会待处理申请提醒。
+ 公会升级通知。
  消息用于提醒，不是最终业务凭证。出现“收到成功消息但页面未变化”时，应以成员关系、公会状态和当前数据为准，再排查刷新延迟。
  
  ## 业务规则
+ 加入、邀请和绑定必须遵守同一运营大区原则。
+ 用户不能通过并发申请或重复邀请同时加入多个公会。
+ 管理员只在授权范围内操作，公会长可以调整其权限。
+ 公会冻结时，资料、设置和成员类操作可能被阻断。
+ 当前成员关系变化不删除历史数据，也不改写已冻结周期。
+ 公会密码属于入会校验信息，不应在运营群或公开文档中传播。
+ 支持者、成员业绩等敏感查询会记录访问情况，运营不可把内部明细随意转发。
  
  ## 常见问题
  
  ### 用户搜索不到可邀请对象
  
  依次检查操作者是否有邀请权限、输入是否为精确标识、目标用户是否存在、双方是否同区、目标是否已有公会，以及是否已有未过期邀请或待处理申请。
  
  ### 用户输入正确密码仍不能加入
  
  密码只是其中一项条件。继续检查大区、用户已有公会、申请频率、公会冻结和该大区是直接加入还是审批加入。
  
  ### 管理员能邀请但不能看成员数据
  
  这是正常的权限拆分。邀请成员、查看成员数据和修改公会信息是三项独立授权。
  
  ### 公会长关闭数据展示后，为什么自己仍能看到
  
  该设置用于控制普通查看者的榜单数值。公会长作为负责人仍保留完整查看能力。
  
  ### 用户离会后为什么历史工资还在
  
  离会只改变当前成员关系，历史工资属于已发生或已结算事实，应继续保留。
