# 公会业务全景与角色生命周期

最后核验日期：2026-08-19

## 适用人群

面向需要快速建立公会业务全局认知的产品、运营、数据和财务同学。阅读后应能判断一个人处于什么角色、一个公会处于什么阶段，以及状态变化会影响哪些功能。

## 功能说明

公会不是单一页面，而是一组相互关联的业务能力：公会身份、成员关系、数据统计、工资结算、成长激励、活动赛事，以及公会与 BD、ACM、运营大区的归属关系。
可以把公会业务理解为四层：

1. 身份层：谁是公会长、管理员、主播、BD 或 ACM 成员。
2. 关系层：用户属于哪个公会，公会归属哪个管理账号和运营大区。
3. 经营层：业绩、上麦、支持者、工资、等级和活动结果。
4. 治理层：运营审核、配置、冻结、转区、结算核对和 ACM 结构管理。
   
   ## 角色与权限边界
   
   | 角色     | 主要能力                           | 默认不能做的事                 |
   | ------ | ------------------------------ | ----------------------- |
   | 普通用户   | 搜索公会、申请建会、申请或接受邀请加入公会          | 查看公会内部敏感数据、管理成员         |
   | 主播     | 查看个人及所在公会允许展示的数据，按规则离会         | 审批成员、修改公会、管理权限          |
   | 公会管理员  | 根据授权邀请成员、查看成员数据或修改公会信息         | 修改自己的授权、越过公会长治理公会       |
   | 公会长    | 管理资料、公告、设置、成员、管理员和申请           | 操作其他公会，绕过大区和冻结限制        |
   | BD     | 负责归属公会的拓展与业绩观察；现行入口通常在 ACM 体系中 | 跨越自身数据范围查看或转移无关公会       |
   | ACM 成员 | 管理允许范围内的成员、公会和数据看板             | 超出模板权限、上级权限和团队额度执行动作    |
   | 顶级 ACM | 管理一棵团队、模板适用能力、团队公会和额度          | 直接改变已冻结历史周期结果           |
   | 平台运营   | 审核、配置、报表、结算核对、状态和结构治理          | 在缺少授权时查看全局数据，跳过高风险预览和确认 |
   
   ### 公会管理员的三类授权
   
   公会长可以分别授予管理员以下能力：
   
   | 授权                                                                 | 作用            |
   | ------------------------------------------------------------------ | ------------- |
   | 查看成员数据                                                             | 查看公会成员的敏感经营数据 |
   | 修改公会信息                                                             | 修改允许编辑的公会资料   |
   | 邀请成员                                                               | 搜索候选用户并发送入会邀请 |
   | 管理员身份和具体授权是两件事。新任管理员可能只有邀请能力，不能因为显示为“管理员”就默认拥有全部权限。公会长本人不受这三项拆分限制。 |               |
   
   ## 公会生命周期
   
   ### 1. 建会申请
   
   公会有两种主要创建来源：
+ 用户主动提交建会资料，等待平台运营审核。
+ 平台运营先创建申请并邀请目标用户确认，用户接受后完成建会。
  同一用户存在有效建会申请时，通常不能重复提交。创建方式还会受到应用、运营大区、ACM 模板和创建额度影响。
  
  ### 2. 创建与初始化
  
  申请通过或用户确认后，系统建立公会身份和公会长关系。此时可能短暂处于初始化状态，前台不应把它当作可完整经营的活跃公会。
  初始化完成后，公会进入正常使用状态，公会长可以完善资料、配置公告、邀请成员和查看数据。
  
  ### 3. 招募成员
  
  成员可以通过申请或邀请加入：
+ 申请加入：用户搜索目标公会，完成密码和大区校验后提交申请；部分大区会直接加入，其他大区由公会管理者审批。
+ 邀请加入：公会长或有邀请权限的管理员精确搜索用户，选择允许的加入时长并发送邀请，用户确认后加入。
  所有路径都要满足同大区、用户当前状态可加入、目标公会可用等条件。
  
  ### 4. 公会内任职
  
  成员加入后默认为普通成员或主播。公会长可以将成员设为管理员，并进一步配置管理员权限。取消管理员后，用户仍可作为普通成员留在公会，其管理权限随之失效。
  
  ### 5. 正常经营
  
  活跃公会可使用的能力包括：
+ 公会主页、资料、公告和成员列表。
+ 日数据、周期数据、排行榜、支持者和明细。
+ 工资、预支工资、等级、荣誉、铭牌和活动。
+ 运营后台报表、导出、财务核对和配置。
  实际能力由应用、大区、周期配置、角色和权限共同决定。
  
  ### 6. 成员退出与踢出
  
  普通成员可以在满足离会冷却规则后主动退出。公会长或获准的管理角色可以踢出成员。操作成功后会更新成员关系，并向相关人员发送通知。
  退出和踢出不会自动改写已经结束周期的历史归属与已结算结果。当前周期的数据归属是否随关系变化，以具体统计截止日和冻结规则为准。
  
  ### 7. 冻结
  
  平台运营可以冻结公会。冻结用于阻止继续经营或限制敏感操作，不等同于删除。冻结期间，资料修改、设置变更、成员操作或其他能力可能被阻断；历史数据仍需保留供查询和审计。
  解冻前应确认冻结原因已经处理，不能仅因为用户反馈“页面不可用”就直接恢复。
  
  ### 8. 转区
  
  平台运营可以创建公会转区任务。转区主要改变公会后续适用的运营大区和配置，不代表历史报表、历史工资或已冻结归属自动搬到新区。
  转区前必须评估：
+ 公会和成员的大区是否一致。
+ 目标大区的周期、指标和工资能力是否兼容。
+ 当前周期是否正在统计或结算。
+ ACM 归属和后台报表是否需要同步调整。
  
  ### 9. 删除
  
  删除是高风险终态操作。普通删除应先满足系统校验；强制删除仅用于明确批准的特殊场景。删除前必须确认成员、未完成申请、当前周期数据、工资、活动和归属关系的处理方式。
  删除不应被当作“修复公会显示异常”的常规手段，也不能以删除重建规避历史追溯。
  
  ## 公会状态与入口
  
  | 状态                                                | 用户侧表现           | 运营关注点          |
  | ------------------------------------------------- | --------------- | -------------- |
  | 无公会                                               | 可看到搜索、申请或邀请相关入口 | 检查用户大区、历史申请和邀请 |
  | 初始化中                                              | 公会已创建但能力未完全开放   | 等待初始化完成，避免重复建会 |
  | 正常                                                | 根据角色展示公会主页和管理能力 | 关注角色、权限和大区配置   |
  | 冻结                                                | 部分页面或操作被阻断      | 先查冻结原因和处理记录    |
  | 已删除                                               | 不再作为正常公会使用      | 保留历史数据和操作审计    |
  | 不同应用和大区不一定展示相同的公会首页入口。没有入口不等于没有公会关系，应先核对业务线和大区能力。 |                 |                |
  
  ## 运营大区与业务线
  
  ### 运营大区决定什么
  
  运营大区至少会影响：
+ 公会入口是否开放。
+ 默认展示的指标类型。
+ 使用周、半月还是月作为周期。
+ 工资、预支工资、等级、榜单和奖励是否可用。
+ 后台报表、导出和 ACM 看板使用哪套口径。
  
  ### Hoki 与 ALFA
  
  Hoki 主线在多个大区共享基础公会能力，但各区的数据和结算政策不同。ALFA 共用一部分公会身份和成员能力，同时拥有独立的数据统计、后台报表、半月结算和 AR 月度分层工资，不能直接照搬 Hoki 口径。
  
  ### 公会与 ACM
  
  ACM 管理的是外管账号层级和公会归属。一个公会在当前时点有直接归属账号；上级账号根据层级和数据范围查看下级及其公会。当前归属可以调整，但历史周期优先使用当时冻结的归属，避免后续转移改变历史结果。
  
  ## 业务规则
+ 用户、公会、BD 或 ACM 账号的大区不一致时，加入、绑定、查询或转移可能被拒绝。
+ 公会长拥有公会内最高权限，但仍受冻结、大区和平台规则限制。
+ 公会管理员的权限必须逐项判断，不能只看身份名称。
+ 当前关系用于当前周期经营；历史周期优先使用冻结关系和已完成结果。
+ 转区、换绑上级或转移公会不应回写已经结束的历史工资和归属。
+ 所有高风险状态变化都应保留操作记录，并在执行前核对影响范围。
  
  ## 常见问题
  
  ### 用户显示“没有公会”，但运营能查到关系
  
  先检查公会是否初始化完成、是否冻结、当前应用和大区是否开放公会页，以及旧客户端是否把部分大区映射为兼容值。不要直接重建关系。
  
  ### 管理员为什么看不到成员数据
  
  管理员身份不等于拥有查看权限。先由公会长核对该管理员的细分授权，再检查公会是否关闭排名数据展示。
  
  ### 转区后为什么历史报表还在原大区
  
  历史报表记录的是业务发生时或周期冻结时的事实。转区影响后续经营，不自动改写历史。
  
  ### 公会冻结后还能否查历史数据
  
  冻结主要限制继续操作。运营后台通常仍需保留历史数据查询和审计能力，具体可见范围取决于后台权限。
  
  ### 为什么同一个 BD 或 ACM 名下的公会数会变化
  
  当前周期通常受实时归属变化影响；历史周期使用冻结归属。还要检查公会是否转移、删除、跨区或不符合当前政策。
