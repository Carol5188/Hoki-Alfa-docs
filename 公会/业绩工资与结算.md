# 业绩工资与结算

最后核验日期：2026-08-19

## 适用人群

面向负责公会工资产品、周期结算、预支工资、财务核对和结算异常处理的产品、运营与财务人员。

## 功能说明

公会结算把周期内已经形成的经营数据转换为主播、公会和适用管理角色的工资或奖励。结算结果涉及真实资金，必须区分实时数据、工资快照、预演结果和正式结算。

## 从业务发生到正式结算

完整链路分为七步：

1. 业务发生：主播收到礼物、产生有效业绩、上麦或完成其他计入政策的行为。
2. 日数据归集：业务事实按 UTC+3 业务日归入公会和主播。
3. 周期汇总：按大区配置生成日、周、半月或月的公会及主播汇总。
4. 评级与工资快照：系统根据当前有效配置计算等级和可追溯的工资参考值。
5. 结算预演：在不执行资金动作的前提下检查人数、金额、配置和数据完整性。
6. 正式结算：执行工资、清理余额和适用奖励等真实业务动作。
7. 结果留档：保存批次、成员结果、失败原因、使用的配置和数据来源，供重试与审计。
   任何一步缺失都可能导致后续为空、跳过或失败。运营不能通过直接重跑正式结算来替代前置数据检查。
   
   ## 业绩与工资的关系
   
   ### 有效业绩
   
   有效业绩是按照大区政策计算后的结算依据。它可能来自原始礼物钻石、红钻/宝石或其他业务事实，不应和原始礼物价值混为一谈。
   
   ### 主播业绩工资
   
   主播业绩工资根据主播周期有效业绩和当期工资政策计算。政策可能是档位金额，也可能是比例计算。是否有工资、进入哪一档、下一档目标和最终金额均以目标周期绑定的有效政策为准。
   
   ### 主播余额工资
   
   部分业务线会根据结算时可处理的钻石余额计算工资，并在正式结算时执行相应余额处理。余额工资与业绩工资是两项独立组成，页面应分别展示，不能只用总工资反推。
   
   ### 公会工资
   
   公会工资表示主播在该公会关系下为公会产生的工资或公会长可获得的部分。具体计算方式受大区和周期政策控制。公会汇总工资不等于所有页面上的“公会总业绩”。
   
   ### 管理层工资
   
   ACM 或 BD 相关工资根据公会归属、账号层级、政策范围和周期快照计算。部分政策按直属公会计算，部分政策按整个下级子树计算。历史周期使用冻结归属，避免后续转移改变历史工资。
   
   ## 工资状态
   
   | 状态                                            | 含义              | 产品与运营处理            |
   | --------------------------------------------- | --------------- | ------------------ |
   | 实时参考                                          | 当前数据直接计算，仅供经营观察 | 不作为发放依据            |
   | 预估                                            | 基于最近成功汇总和工资快照计算 | 明确标注结果会变化          |
   | 待结算                                           | 周期已结束但尚未正式完成    | 检查汇总和预演            |
   | 已结算                                           | 正式结算成功          | 作为正式结果展示           |
   | 部分失败                                          | 同一批次部分主播成功、部分失败 | 只重试失败对象，避免重复处理成功对象 |
   | 失败                                            | 批次未完成或关键前置条件不满足 | 先修复原因，再按相同周期重试     |
   | 人工复核                                          | 资金结果无法自动确认      | 禁止自动重放，交由财务和技术联合核对 |
   | 空工资与零工资不同：零表示政策适用但结果为零；空表示政策不适用、没有成功快照或数据不可用。 |                 |                    |
   
   ## 周期差异
   
   | 周期                                                                                                         | 经营含义             | 结算注意点                        |
   | ---------------------------------------------------------------------------------------------------------- | ---------------- | ---------------------------- |
   | 日                                                                                                          | 日常指标或特定政策的最小统计单元 | 多数情况下不直接代表发薪周期               |
   | 周                                                                                                          | 独立于半月的结算周期       | 即使日期与半月重叠，也不跨周期冲抵            |
   | 半月                                                                                                         | 上半月和下半月分别结算      | 常用于钻石业绩、工资和余额处理              |
   | 月                                                                                                          | 自然月范围            | 常用于 TR/CIS 宝石汇总和 ALFA 月度管理工资 |
   | 统一结算能力当前覆盖 ARAB、PHL、SASIA 和 AFRICA，支持的具体周期以大区有效配置和运营排期为准。ALFA 使用独立结算逻辑，TR/CIS 主要使用月度宝石经营口径，不能直接套用统一钻石工资流程。 |                  |                              |
   
   ## 红钻与宝石结算
   
   红钻/宝石型业务需要区分即时结算和次日结算，两者在页面和报表中应分别展示：
   
   | 类型                                                                           | 业务含义               | 运营核对重点                   |
   | ---------------------------------------------------------------------------- | ------------------ | ------------------------ |
   | 即时结算                                                                         | 礼物行为完成后即可计入的宝石结果   | 核对礼物发生时间、有效性和即时结果        |
   | 次日结算                                                                         | 在下一业务日完成确认后计入的宝石结果 | 按 UTC+3 核对归属日，不与即时结果重复计算 |
   | 修正或冲抵                                                                        | 对已记录结果进行补正、撤销或抵扣   | 保留原记录与调整记录，按调整后的净结果解释    |
   | 月度报表汇总的是目标周期内各类结果及其净影响。次日结算可能使月末礼物在下一业务日才完成确认，因此核对月度差异时要同时看礼物发生日、结算确认日和调整记录。 |                    |                          |
   | 修正或冲抵不能通过删除历史记录来处理，也不能把负向调整隐藏为零。若同一礼物同时出现重复入账和冲抵不完整，应暂停人工补发并升级财务和技术联合核对。     |                    |                          |
   
   ## 工资快照
   
   工资快照用于把“某一业务日、某一周期、某一套政策下的可计算工资”固定下来。它有三个重要作用：
+ 支撑用户端的工资预估和预支额度。
+ 让正式结算可以追溯到当时使用的数据与政策。
+ 避免用户查询时每次读取实时数据产生金额漂移。
  没有成功工资快照时，用户端应关闭依赖快照的能力，不回退到旧口径或临时实时计算。
  
  ## 预支工资
  
  ### 适用范围
  
  现行预支工资以半月工资快照为基础。是否开放、可预支比例、次数、日期范围和排除公会由大区当前配置决定。
  
  ### 可预支额度
  
  系统综合以下因素计算剩余额度：
+ 当前半月成功工资快照中的主播业绩工资。
+ 业绩是否达到全额预支条件。
+ 所在大区的预支比例。
+ 本周期已经成功或占用中的预支金额。
+ 最大次数、开放日期和公会排除规则。
  剩余额度按整美元处理。配置门槛和比例会变化，运营必须以后台当前有效配置为准，不引用旧截图或历史文档数值。
  
  ### 提交流程
1. 页面展示最大次数、已使用次数、剩余额度和是否可预支。
2. 用户选择不超过剩余额度的金额并确认。
3. 系统先占用本周期额度，再执行入账及后续兑换流程。
4. 成功后更新记录和剩余额度。
5. 结果不明确时转人工复核，不自动猜测或重复执行资金动作。
   同一次提交具有防重复保护。用户连续点击或网络重试不应产生两笔有效预支。
   
   ### 预支失败排查
   
   | 现象         | 优先检查                        |
   | ---------- | --------------------------- |
   | 按钮不可用      | 大区开关、开放日期、成功快照、剩余额度、次数和公会排除 |
   | 可预支金额为零    | 快照工资、已占额度、比例和取整结果           |
   | 提交后一直处理中   | 是否超过正常处理窗口，是否已进入人工复核        |
   | 用户称到账但记录失败 | 同时核对预支记录、美元账单、兑换账单和最终金币记录   |
   | 用户重复提交     | 检查是否复用了同一请求，不要人工再次发起        |
   
   ## 自动处理顺序
   
   常规周期应按以下业务顺序运行：
6. 补齐需要纳入的上麦和日业绩数据。
7. 生成目标周期的主播汇总和公会汇总。
8. 对已结束周期评定公会等级。
9. 在汇总和等级确认后发送适用的升级通知。
10. 生成主播工资快照。
11. 先做同范围结算预演。
12. 核对预演后执行正式结算。
13. 更新 ACM 等需要周期快照的管理看板。
14. 巡检长时间未完成的预支或结算记录。
    补数据、重算汇总、重新评级和正式结算不是可以随意交换顺序的独立按钮。
    
    ## 结算前检查
    
    | 检查项                                                       | 通过标准                 |
    | --------------------------------------------------------- | -------------------- |
    | 大区和周期                                                     | 目标大区支持该结算周期，起止日正确    |
    | 周期状态                                                      | 生产正式结算只处理已结束周期       |
    | 汇总数据                                                      | 公会和主播汇总成功，目标指标齐全     |
    | 配置                                                        | 目标周期已绑定有效配置，重试时沿用原绑定 |
    | 工资快照                                                      | 需要快照的链路已生成成功结果       |
    | 预演                                                        | 人数、工资、余额处理和奖励数量符合预期  |
    | 并发                                                        | 没有旧任务或同周期任务正在处理相同范围  |
    | 异常名单                                                      | 已明确排除、补跑或人工处理对象      |
    | 生产环境不得为了赶进度强行结算尚未结束的当前周期。测试环境的提前验证也会产生真实资金动作，必须限定测试账号和范围。 |                      |
    
    ## 结算后核对
15. 确认批次为成功或符合预期的部分失败。
16. 核对总公会数、总主播数、成功数、失败数和跳过数。
17. 核对工资总额、余额处理总额和奖励总量。
18. 检查失败对象的具体阶段和原因。
19. 确认成功对象不会在补跑时再次执行资金动作。
20. 对预支工资占用和正式工资进行周期内一致性核对。
21. 确认用户端、运营后台和 ACM 看板已刷新到目标周期。
    
    ## 重试与防重复原则
+ 同一大区、同一精确周期只能串行结算。
+ 已成功的主播在同周期重试时应跳过真实资金动作。
+ 失败主播允许补跑，但必须沿用目标周期的政策和来源范围。
+ 当前关系变化不能改变已冻结历史归属。
+ 资金调用结果不明确时禁止自动重放，必须人工核账。
+ 数据修复应先预览范围，再由技术按批准范围执行；运营不直接操作底层修复。
  
  ## 需要技术介入的情况
+ 目标周期缺少成功汇总，重算后仍不完整。
+ 同一对象出现重复或冲突的成功资金记录。
+ 结算显示成功，但钱包和账单无法对齐。
+ 批次长期处于处理中，且没有明确可重试状态。
+ 历史周期归属或配置快照缺失，无法证明当期口径。
+ 转区、跨团队迁移与结算同时发生，导致范围不确定。
+ 大量对象以同一未知原因失败，疑似系统性问题。
  
  ## 业务规则
+ 所有周期边界按 UTC+3。
+ 正式结算优先使用精确周期汇总和当期绑定配置。
+ 周、半月和月是独立结算范围，不因日期重叠自动冲抵。
+ 当前周期金额是预估，历史成功结算金额是正式值。
+ 预支工资占用当期额度，人工复核中的订单不能当作失败释放。
+ 重试只处理失败或未完成对象，不重复处理成功对象。
+ 配置变化不能静默改写已经冻结的历史工资。
  
  ## 常见问题
  
  ### 周期已结束，为什么工资仍显示预估
  
  周期结束不等于正式结算完成。检查成功汇总、工资快照和结算批次是否已经生成并被页面读取。
  
  ### 预演通过后为什么正式结算仍可能失败
  
  预演不执行真实资金动作。正式执行期间仍可能遇到账户状态、并发变化、钱包异常或配置被修改。
  
  ### 为什么补跑后总人数变少
  
  核对补跑范围是否限定了公会或主播、是否使用同一周期配置，以及部分成功对象是否被正确跳过。
  
  ### 为什么当前月 ACM 工资与公会工资相加不一致
  
  部分管理政策允许同一公会进入不同层级账号的工资基数，不能把所有层级工资头简单相加解释为物理公会总工资。
  
  ### 为什么预支记录进入人工复核
  
  系统无法可靠判断资金动作是否完成时，会停止自动重试以避免重复发放。需要联合核对完整账单链路。
