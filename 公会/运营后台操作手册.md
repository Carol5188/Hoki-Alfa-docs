# 运营后台操作手册

最后核验日期：2026-08-19

## 适用人群

面向使用运营后台处理建会、成员、公会配置、数据报表、结算、活动和 ACM 治理的日常运营、数据运营、财务运营及平台主管。

## 功能说明

运营后台提供公会管理、主播管理、数据报表、配置发布、结算核对、活动维护和外管治理。实际菜单由后台账号权限和大区数据范围决定；看不到菜单时，先核对授权，不要用其他账号代操作。

## 通用操作原则

1. 先确认当前应用、环境和登录账号。
2. 选择正确大区，再选择公会、主播或 ACM 团队。
3. 时间统一按页面标注的 UTC+3 业务日期和周期处理。
4. 修改前记录当前值、影响对象和生效时间。
5. 有预览的高风险操作必须先预览，再按预览结果提交。
6. 提交后以后台状态和业务结果为准，不只看“操作成功”提示。
7. 不通过删除重建、重复发放或重复结算绕过异常。
   
   ## 建会与公会管理
   
   ### 建会审核
   
   “建会审核”展示用户主动提交的待审核记录。运营需要核对用户、公会名称、联系方式、国家、证明材料、密码和备注。
   
   | 操作前确认                                   | 处理结果  | 成功判断                 |
   | --------------------------------------- | ----- | -------------------- |
   | 用户未拥有冲突公会或申请，资料完整                       | 通过或拒绝 | 申请状态更新；通过后公会和公会长关系建立 |
   | 拒绝时应填写可对外解释的业务原因。资料问题应让用户修正，不要先通过再删除公会。 |       |                      |
   
   ### 后台发起建会
   
   运营可以为目标用户发起等待用户确认的建会申请。该动作只生成邀请，用户接受后才创建公会。
   操作前确认：
+ 目标用户身份和运营大区正确。
+ 公会资料经过业务确认。
+ 用户没有冲突公会或有效申请。
+ 如果由 ACM 发起，目标直接归属、创建权限和团队额度正确。
  
  ### 公会列表
  
  公会列表支持按公会、负责人、区域或状态筛选，并提供新增、修改、冻结、删除等管理动作。列表也是进入成员、数据和历史操作的基础入口。
  
  ### 修改公会
  
  运营可修改允许维护的基础资料。修改前应区分“公会主档资料”和“公会长用户资料”，不要用修改公会资料解决用户账号信息错误。
  成功后确认列表和用户端主页均已刷新。名称、头像等当前展示资料可能影响历史榜单的视觉展示，但不改变历史名次。
  
  ### 冻结与恢复
  
  冻结用于限制公会继续经营。操作前必须记录原因、期限和恢复条件，并确认是否处于统计、结算或活动周期中。
  冻结后检查：
+ 用户端敏感操作已被阻断。
+ 历史数据仍可查询。
+ 当前结算和活动是否需要排除或人工处理。
  恢复前确认原原因已解除，并检查冻结期间是否发生成员、大区或归属变化。
  
  ### 删除与强制删除
  
  普通删除遵守系统校验。强制删除可能绕过部分限制，只能按批准工单执行。
  必须确认：
+ 公会成员和管理员的后续处理。
+ 待处理申请和邀请。
+ 当前周期业绩、工资、预支和结算状态。
+ 活动报名、荣誉和奖励。
+ ACM 直接归属和历史冻结归属。
  提交后需要核对公会状态、成员关系和后台报表。历史业务事实应继续保留。
  
  ## 主播与成员管理
  
  ### 主播列表
  
  后台可按公会和用户筛选主播，查看身份与经营数据，并执行新增、批量添加、修改或移出。
  
  ### 批量添加主播
  
  批量操作前应先校验：
+ 所有主播真实存在且状态可加入。
+ 主播与目标公会同区。
+ 主播没有冲突公会关系。
+ 导入数量和目标公会无误。
  批量结果要按成功、跳过和失败分别核对。不得因为部分失败就整体重复导入。
  
  ### 移出主播
  
  移出只改变当前关系，不删除历史业绩和工资。操作前检查当前周期是否即将结算，并告知业务方可能影响当前周期归属展示。
  
  ### 公会长和管理员权限
  
  公会长负责用户端管理员授权。后台排查时可以核对管理员身份和细分权限，但不应在没有业务授权时替用户修改权限。
  
  ## 公会和主播数据报表
  
  ### 区域报表
  
  后台提供 ARAB 主线和 PHL、SASIA、AFRICA、TR、CIS 等区域的公会、主播报表。不同区域可能展示钻石业绩、红钻/宝石、日榜或周期工资等不同字段。
  使用要求：
+ 先选大区，再选周期。
+ 核对页面标题和指标单位。
+ 页面查询和导出使用相同筛选。
+ 不跨区直接比较不同指标。
  
  ### 统一业绩报表
  
  统一报表将不同大区的公会和主播汇总放入一致的筛选和导出框架。运营可以配置各大区可用字段和周期，再查询列表、汇总统计和导出。
  保存报表配置前，确认目标大区的统计链路能实际产出所选字段。打开一个没有数据来源的字段，只会造成长期空值。
  
  ### 主播个人看板
  
  个人看板支持：
+ 配置各大区可见指标。
+ 按主播或公会查询详情。
+ 查看支持者。
+ 查看主播预支工资明细。
+ 查看公会内主播排名。
  查询主播时要确认其在周期结束日所属公会；当前所属公会不一定等于历史周期所属公会。
  
  ### 导出管理
  
  部分大数据量导出异步生成。运营发起后应到下载任务中确认状态，不要连续重复点击。导出文件应包含大区、报表类型、周期和生成时间，便于后续对账。
  
  ## 充值、财务和工资名单
  
  ### 充值数据
  
  公会管理中可以查看主播充值记录、月度记录、公会周/月汇总和当前周/月统计。时间口径按 UTC+3。
  充值数据和公会业绩是不同业务域。充值汇总不能替代礼物业绩或工资结算数据。
  
  ### 公会财务
  
  财务页面用于查看公会财务记录、记录管理员佣金，以及汇总管理员佣金。修改佣金会影响关联记录，操作前必须保留业务批准依据并核对适用周期。
  
  ### 提现工资用户
  
  后台可以查询和维护公会提现工资用户名单。该名单属于资金相关配置，修改前要核对公会、用户和生效范围，修改后需要由财务验证提现流程。
  
  ### 批量工资
  
  批量工资页面用于集中处理允许的工资发放或结果查看。执行前必须使用目标周期的已确认数据，不能把当前预估直接当作正式发放清单。
  
  ## 公会配置管理
  
  ### 配置类型
  
  公会配置覆盖等级、业绩指标、结算周期、工资、预支、奖励、看板字段和 ALFA 月度管理工资等能力。具体可配置项由应用和大区决定。
  
  ### 当前配置
  
  当前配置代表正在生效的完整业务规则。运营可以查看、保存当前槽位，或在允许时调整单项并立即生效。
  立即生效适合低风险且明确允许实时变化的配置。工资、结算、等级等周期敏感配置应优先在周期边界发布，避免同一周期前后口径不一致。
  
  ### 未来配置
  
  未来配置用于预先准备下一周期规则：
1. 选择目标大区和合法周期边界。
2. 基于当前完整配置创建未来版本。
3. 修改需要变化的单项。
4. 设置生效时间。
5. 复核完整差异后等待生效。
   未来配置可以调整时间、撤回某个单项或关闭整个未来槽位。关闭前确认没有其他部门依赖该版本上线。
   
   ### 发布历史
   
   后台可查看配置历史版本、发布时间线、发布详情和基础版本。出现周期结果争议时，应先定位目标周期使用的版本，不要只查看当前配置。
   
   ### 取消配置
   
   只允许取消尚未生效且处于可取消位置的版本。已经生效并参与结算的配置不能通过简单取消抹去，应走新的修正版本和业务补偿流程。
   
   ### 配置发布检查
   
   | 检查项 | 要求                     |
   | --- | ---------------------- |
   | 大区  | 目标大区正确，不使用默认区代替        |
   | 完整性 | 依赖的指标、周期、工资和奖励均存在      |
   | 时间  | 生效时间位于系统认可的周期边界        |
   | 差异  | 已复核新增、修改和删除项           |
   | 影响  | 已确认用户端、报表、结算和 ACM 看板影响 |
   | 回退  | 明确未生效如何撤回、已生效如何发布修正版   |
   
   ## 荣誉与铭牌
   
   ### 荣誉配置
   
   运营可以创建、更新和查看荣誉资源，包括多语言名称、墙面、徽章和动画。上线前需要在目标语言和终端验收资源完整性。
   修改荣誉配置会影响历史荣誉的当前展示，不能改变公会是否曾获得该荣誉。
   
   ### 铭牌管理
   
   铭牌页面支持查询当前生效记录并更新等级和有效期。操作时间使用 UTC+3。
   人工更新前检查自动评级是否即将执行；人工补偿应记录原因和到期时间，避免形成永久例外。
   
   ## 公会 PK 管理
   
   运营可在赛事列表中创建比赛、配置赛段、开始赛事、查看参赛公会和对阵、填写成绩并处理晋级。
   标准操作顺序：
6. 创建赛事并确认报名时间。
7. 配置全部赛段和时间。
8. 开放并观察报名。
9. 到期后开始赛事。
10. 按赛段核对和录入成绩。
11. 处理晋级并检查下一阶段对阵。
12. 确认冠亚季军和活动结束状态。
    赛事开始后修改赛段或成绩属于高风险操作，必须保留证据并核对对下一阶段的影响。
    
    ## 自动任务运行记录
    
    公会业绩任务记录页面提供运行列表、汇总和详情，用于判断目标大区、周期和处理范围是否成功。
    运营主要关注：
+ 业务处理名称和时间。
+ 大区、周期和目标范围。
+ 成功、部分失败或失败状态。
+ 处理数量、跳过数量和失败摘要。
+ 是否存在同范围重复运行。
  页面中的底层参数和实例信息用于技术排查，产品运营不应自行复制修改后重跑。
  
  ## 周期结算结果
  
  结算结果页面提供批次列表、汇总和详情。标准核对包括：
+ 大区与精确周期。
+ 预演或正式执行。
+ 总数、成功数、失败数和跳过数。
+ 主播工资、余额处理和奖励状态。
+ 失败原因及是否允许补跑。
  部分失败时只处理失败对象。对已经成功的资金动作重复发起属于严重风险。
  
  ## 公会转区
  
  转区页面用于创建和查看公会转区记录。转区只影响后续适用的大区规则，不自动搬迁历史数据。
  操作前确认：
+ 公会当前和目标大区。
+ 成员大区是否需要先调整。
+ 当前周期统计与结算状态。
+ 目标区指标、工资、等级和报表是否就绪。
+ ACM 归属和数据范围是否兼容。
  提交后检查转区记录状态、公会当前大区、缓存刷新、用户端入口和目标区报表。
  
  ## ACM V3 与 BD 后台
  
  ACM V3 后台负责账号树、成员、公会归属、模板、权限、额度、状态、团队迁移和周期报表。存量 BD 报表仍保留部分区域明细和汇总。两者的完整边界见[大区业务线与新旧版本差异](07-大区业务线与新旧版本差异.md)。
  
  ## 高风险操作清单
  
  | 操作         | 主要风险             | 成功后必须核对        |
  | ---------- | ---------------- | -------------- |
  | 强制删除公会     | 关系、结算、活动和归属断裂    | 公会状态、成员、历史数据   |
  | 公会转区       | 后续规则切换、当前周期范围不确定 | 新区入口、配置、报表和归属  |
  | 立即发布配置     | 周期内口径变化          | 版本、生效时间和受影响页面  |
  | 正式结算或补跑    | 重复资金动作           | 批次、成功对象和钱包结果   |
  | 修改佣金或工资名单  | 资金结果变化           | 批准依据、用户和金额     |
  | 修改铭牌有效期    | 覆盖自动评级           | 等级、起止时间和展示     |
  | PK 提交分数或晋级 | 排名和下一阶段变化        | 对阵、排名和晋级名单     |
  | ACM 团队迁移   | 权限、额度、归属和可见范围变化  | 预览、账号树、公会和历史范围 |
  
  ## 不可自行处理的异常
+ 资金结果和业务状态冲突。
+ 同一周期出现重复成功记录。
+ 配置版本无法确认或历史周期缺少绑定。
+ 转区或团队迁移后历史归属发生变化。
+ 大批量报表与用户端持续不一致。
+ 自动任务反复失败且错误原因相同。
+ 删除、冻结或恢复后关系状态不一致。
  遇到以上情况应停止重复操作，保留页面筛选、周期、对象、时间和操作记录，交由技术与财务联合处理。
  
  ## 业务规则
+ 后台菜单权限和数据范围是两层控制，能看到按钮不代表能操作所有大区或团队。
+ 高风险治理操作必须先预览影响，再提交。
+ 当前配置与历史周期配置必须分开查看。
+ 页面查询、汇总和导出必须使用同一筛选口径。
+ 运营操作不能修改已经冻结的历史事实。
+ 操作成功提示只是受理结果，必须继续验证业务状态。
  
  ## 常见问题
  
  ### 为什么同事有菜单，我没有
  
  先核对角色权限、应用和大区数据范围。不要共享账号或让他人代执行高风险操作。
  
  ### 配置已保存，为什么用户端没变化
  
  检查保存的是当前还是未来配置、生效时间、目标大区和缓存刷新；周期敏感配置可能要到边界才生效。
  
  ### 导出成功但数据还是旧的
  
  文件记录的是生成时数据。核对生成时间和筛选，并在统计完成后重新生成，不要把旧文件当作最新结果。
  
  ### 结算结果部分失败怎么办
  
  先确认成功对象已被保护，再按失败原因修复并限定范围补跑。不得整体重复正式结算。
  
  ### 转区完成后旧报表还有数据
  
  这是正常的历史保留。转区不改写过去发生或冻结的记录。
