### 3.1 性别字段与关系资格

平台性别继续非必填，但本期所有关系类型均不读取性别做资格判断。兄弟、闺蜜、挚友与CP在创建、邀请、接受和关系存量兼容中，均不因性别未填写或性别值不同而拦截。

- 候选列表不提供性别筛选，不展示“性别不符合”“请先填写性别”等关系资格原因；用户未填写、填写男/女或其他平台允许值，均按同一资格路径继续校验。
- 服务端不得以`gender`、`gender_is_set`或历史默认性别值作为关系创建/接受条件，也不得因性别字段缺失返回关系资格错误码。资料查询失败不能被误判为关系位满、亲密度不足或其他资格错误。
- 发送与接受仍需复核好友关系、同对象关系冲突、重复申请、关系门槛、双方关系位、账号/版本和其他既定资格；资格变化只按这些条件处理。
- 存量正式关系继续有效，不因性别资料新增、修改、删除或字段迁移自动解除、切换类型、退款或清除日/周任务；历史pending不因性别变化失效。
- 关系候选页如因平台通用资料展示需要保留性别信息，只能作为非资格信息，并不得改变可选状态、排序、Toast或按钮文案。

## 4. 其他亲密关系豆腐块

### 4.1 排序与卡片

- **兄弟、闺蜜、挚友已建立卡统一按服务端关系等级降序排列，不按类型分组。**CP独占位不参与。
- 使用各关系现行服务返回的展示等级；不为排序新增CP等级曲线，不以亲密值、今日增长、建立时间或付费属性替代主排序。
- 同级稳定次序：按关系建立时间排序；时间相同再按`relationship_id`升序，保证结果稳定。
- 展示顺序为：已建立关系 → 待确认席位 → 可邀请空位 → 下一席解锁入口。后三组各自按真实席位编号升序。
- 展示排序不重分配`slot_id`，不更改免费/已购属性、容量、占位或邀请对象。点击卡片传`relationship_id`，点击空位传真实`slot_id`，不能用视觉位置当业务席位。
- 卡片保留伙伴头像、昵称、关系称谓、关系等级及原有展示信息。无关系时显示3个免费空位与`0/3`；已扩容按真实容量展示。
- 进入页面、成功建立/解除、等级更新后重新拉取。保持正在浏览关系的可见位置，避免刷新后跳到另一对象；LTR从左侧、RTL从右侧展示最高等级。
- 等级暂缺时显示“—”并放在已建立卡尾部，重拉后恢复排序，不伪造Lv1。

排序示例：兄弟Lv12 → 挚友Lv8 → 闺蜜Lv5 → 待确认 → 空位。示例仅说明顺序，不代表等级配置。

`空位/建立关系 → 选类型 → 本人资格（空位） → 选好友 → 双方好友/冲突/空位/500门槛校验 → 发送 → pending → 对方接受时复核 → 建立并按等级排序`

#### 4.2.1 候选好友列表规则

展示头像、昵称、当前双人亲密值、关系类型、可邀请状态和具体不可邀请原因。候选列表不以性别作为筛选条件、排序条件、可选条件或Toast触发条件；未填写性别与已填写性别的用户展示和可选逻辑一致。

候选列表保留不合格好友，明确真实原因，避免用户以为好友消失；合格行可选，不合格行不能成为选中对象，但可点击查看原因并展示对应Toast。发送按钮只在选中对象当前合格时可用；前端禁用不能替代发送时服务端复核。双方空位、好友关系、已有关系/重复申请和亲密度门槛分别校验，候选显示“可邀请 / 亲密关系位已满 / 已存在关系或申请 / 亲密度还差{value}”等状态，不展示对方每一席的私有关系信息。

| 本人/好友状态 | 处理结果 |
|---|---|
| 性别均已填写、仅一方填写或双方均未填写，其他条件满足 | 可邀请；不因性别差异阻断 |
| 任一方亲密关系位已满、亲密度达标 | 不可邀请；展示对应席位已满Toast |
| 双方尚有已解锁空位、好友关系和其他条件满足 | 可邀请 |
| 亲密度不足 | 不可邀请；展示差值和亲密度不足提示 |
| 已有同对象关系、重复申请或好友关系失效 | 不可邀请；展示对应关系/申请原因 |

行状态和按钮在切换关系类型、返回资料页、页面刷新/回前台、申请/席位变化后重新拉取。保留当前选择仅限仍符合条件；资格失效则取消选中并说明，不自动换好友或换关系类型。

#### 4.2.2 分场景提示与校验优先级

同次校验返回稳定业务错误码，客户端按码展示对应文案。建议优先级：账号/好友/已有同对象关系或重复申请 → 本人对应位 → 好友对应位 → 亲密度门槛 → 其他关系资格；各Toast相互独立，不能把位满、关系冲突或门槛不足写成网络失败。同一点击只提示优先原因，修正后重新校验其他条件。

#### 4.2.3 双端空位与并发规则

- 可用亲友位＝已解锁容量−正式关系占用−有效pending占位，最小为0；3个免费位和已购第4/5位共用计算，同一申请在同一账号只占一次，CP独占位不计入。服务器返回可邀请及原因，客户端不能只根据亲密度或本人的列表推断好友有空位。
- 发送事务同时核验双方，并为双方各绑定一个可用亲友`slot_id`（好友侧由服务端选择真实空位）。申请、双方占位同时成功才返回发送成功；任一方无位则全部不创建，不发IM，不亮新增申请红点，不单边占位。邀请前不自动扩容或释放别人的申请。
- 两名邀请者争抢同一好友最后一个位时，仅一个创建成功；另一方返回好友位满错误，使用上表指定Toast。重复提交/超时按原请求ID查询，不再占第二席。
- 接受时复核**本申请预留位仍有效、可转为正式关系**；不能直接要求“当前剩余位大于0”，否则本申请占着最后一位会误报满位。自己的有效预留位可以转正式，其他关系/pending的位不能抢占。
- 拒绝/超时原子释放双方本申请占位；接受转正式占用，关闭/查看/删IM不释放。旧申请若缺双端预留，在接受时按原子事务补足空位并建立；无法补足就停在pending、展示本人或好友位满，可拒绝或按原截止时间到期，不延长、不自动撤回。
- 席位、关系冲突或门槛资格失败不创建关系、不触发成长/日周任务；接受失败保留唯一pending和原有效期，恢复资格后重拉。拒绝不受亲密度或空位限制，不能把接收方困在无法结束的申请中。

## 7. 红点与独立存储规则

### 7.1 红点定义与展示

**红点 = 当前用户存在未读的关系申请消息或未读的关系处理结果消息。**

**点击对应卡片并成功打开详情，即将实际展示的消息版本标记为已读；之后关闭详情、同意或拒绝，均不恢复同一消息版本的红点。关闭详情时，申请仍保持“待处理”，用户可再次打开处理。**

- 红点展示在Me的CP&Best Friends行、个人主页CP & Friends内CP标题右侧信封，以及对应未读消息卡片；两个页面入口共用账号摘要。
- “待处理”是申请业务状态，“已读/未读”是消息状态，独立计算；看过但未处理的申请可以没有红点。
- 入口红点只在该账号仍有任意未读申请/结果时显示；打开一张卡只消除该版本的未读提醒，不清其他卡片。未读全部清除后入口红点消失，即使仍有已读待处理申请。
- 仅进入个人主页、进入消息列表、切换Tab、卡片曝光或滚动列表均不标已读。申请卡和结果卡统一在用户点击并成功打开详情后标已读。
- 新申请或已有申请产生接受、拒绝、过期及适用的协议解除新结果时，生成新的消息事件版本并置未读，重新点亮相关卡片及账号入口。重复推送、刷新、重登、相同状态回放不生成新版本，不重复点亮。
- “收到的申请”待处理数仍按有效待我处理申请计算；已读不会减少此计数。发出申请等待回应不单独产生发起方未读提醒。
- 发出后的建立申请不可撤回，本版不新增撤回消息或状态。

### 7.2 事件与红点行为

| 事件 | 申请业务状态/记录行为 | 红点行为 |
|---|---|---|
| 收到有效新申请 | 申请为待处理，收到页待处理数增加；生成接收方未读申请事件 | 对应卡片及两个入口亮红点 |
| 仅点击页面入口、进入列表、切Tab、列表曝光/滚动 | 不改变申请，不标消息已读 | 红点保持 |
| 点击申请卡并成功打开详情 | 该申请事件版本已读，申请仍待处理，待处理数不减少 | 当前卡片红点消失；入口仅在还有其他未读消息时保留 |
| 打开详情后关闭/系统返回 | 消息保持已读，申请仍待处理；不拒绝、不取消、不释放位或延长有效期 | 同一版本不恢复红点 |
| 接受/拒绝成功 | 服务端更新为已接受/已拒绝，移除对应待处理数并生成结果事件 | 发起方的新结果未读并亮红点；操作者本端成功展示的结果版本可直接标已读，不再提醒自己刚看过的结果 |
| 接受/拒绝失败或查询中 | 已查看的申请消息仍已读；申请状态以查询结果为准 | 不因点击失败或重试重新点亮旧版本；若服务端确认有新结果，则按新事件提醒 |
| 申请服务端过期 | 移出待处理，按现有规则释放占位；生成双方过期结果事件 | 对尚未查看新结果的账号重新亮红点；先前看过申请不等于看过过期结果 |
| 发出申请等待对方回应 | 我发出的卡显示等待回应；不算待我处理 | 发起方不因自己的等待状态亮红点 |
| 发出申请获得接受/拒绝等新结果 | 生成发起方未读结果事件 | 卡片及入口亮红点；点击并成功打开结果详情后才消除，不因列表曝光自动清除 |
| 已读卡片获得新的状态结果 | 同一卡片更新到新事件版本，业务状态以最新结果为准 | 新版本未读，重新亮红点 |
| 多张卡片并存 | 每张卡按当前用户与实际查看版本独立读状态 | 只消当前卡片；其他未读存在则入口红点保持，仅剩已读待处理卡时入口无红点 |
| 多设备查看或处理 | 已读记录账号级同步，申请以服务端最新状态为准 | 同一版本已读后各设备同步消红点；旧设备确认不能误清另一设备新产生的结果 |
| 列表/详情加载失败、快速关闭未展示内容 | 不标已读，不把未知计数当0 | 不清已有提醒 |
| 已读确认失败或超时 | 保留幂等补报，重拉服务端读状态；不批量清除其他版本 | 成功确认后更新账号摘要；同步恢复前不宣称跨设备已清除 |

### 7.3 已读记录与新结果版本

- **标已读时机**：用户点击申请/结果卡，最新详情内容成功展示后，客户端提交当前用户实际展示的`record_id + message_event_id + event_version`。同源IM卡详情也使用此接口；仅IM气泡曝光或IM已读不视为关系消息已读。
- 申请事件与结果事件均有稳定事件ID、类型及版本；后台申请`status`与消息`read_state`分开保存。仅已读确认不修改申请状态、占位、订单、有效期或日/周任务。
- 同一申请可复用一张列表卡，但新结果必须产生新的消息事件版本；读取旧申请版本不能将随后产生的接受、拒绝或过期结果提前标已读。
- 每次已读确认仅覆盖实际展示版本及该卡此前版本，不能覆盖未点击的其他卡片，也不能覆盖加载期间刚生成但尚未展示的新结果。详情更新过程中，只有新结果成功展示后才确认该版本已读。
- 操作者在当前详情成功看到自己提交后的结果，可将该结果版本同步标已读；如果结果未展示、响应不明或另一设备处理，新的结果仍按未读规则提醒。对方账号独立未读，不能一起标已读。
- 已读确认幂等、账号级保存并跨设备同步；关闭、返回、刷新、重登、重复通知不会将已读的同一版本重置未读。同步失败补报原版本，不标记“全部已读”。
- 现有`result_version`可作为结果事件映射来源，但须同时支持申请消息已读和新事件区分；不能只保存结果已读，也不能用`pending_to_me_count > 0`直接计算入口红点。
- 终态消息展示与保留期限沿用现有策略；有效待处理申请始终可查，包括已读但尚未回应的申请。

### 7.4 独立存储与存量兼容

申请/关系服务为事实源，IM只承担通知与跳转。以下三类数据独立：申请业务状态、账号级申请/结果消息已读状态、IM消息及会话状态。

1. 发起成功先持久化申请及占位，写入双方可查询记录和接收方未读申请事件，再异步投递IM通知；IM失败重试，不回滚申请，也不因通知重试生成新的未读事件。
2. 删除IM不级联删除申请、消息事件、订单、席位、关系或独立读状态；通过列表仍能查看和处理，成功打开详情后再按本版标已读。
3. 列表按当前登录用户查询，不要求聊天会话ID或对方消息ID；双方只能查询自己参与的申请及各自的读状态。
4. 接受/拒绝按申请ID幂等；业务结果与结果事件唯一，不能因双入口或多设备重复操作而重复建立关系、发奖或生成新结果提醒。
5. 灰度时补入已有有效待处理申请及消息事件，已读申请也不能漏出列表。有可核验的同源详情查看记录/旧已读版本时映射为已读；没有可信记录时按未读接入，不能根据“IM已读/会话被删/申请仍待处理”推断。事件迁移幂等，不反复重置已读；具体历史字段映射见第16节实施核验。
6. 仅有旧IM记录而无持久申请实体时须补齐来源或恢复。解除后不返回旧关系内容，必要申请结果仅保留状态/时间；不通过结果卡恢复旧礼物、纪念、流水或寄语详情。

- 接受成功后，刷新双方CP展示、关系卡、每日及周任务和原等级/EXP服务；将本申请合格实付求婚戒指按9.1.4绑定新CP关系，计入建立当天日“送份礼物”及建立当周“关系升温”。关系初始化及任务补记幂等，不注入v5.19新100级体系的1,000起点或执行新等级重算。

- 关系已建立但IM结果投递失败时，列表显示已接受；IM重试不重复创建关系。应用退出、重登或删除聊天后均可恢复服务端状态。

#### 9.1.3 周期、共享与回退

- 每段关系独立统计，双方共享进度与一次奖励：**每日最多40、每周最多80**。任一方完成单方可满足的任务即推进双方同一实例；双人条件仍须双方各自达标。双方页面各显示同一奖励，不发成两份。
- 刷新时区沿用当前关系分区：每日00:00、每周一00:00；服务端下发`cycle_id/timezone/next_reset_at`。建立后开始统计，不补算建立前互动；仅本次结成CP所用求婚戒指按9.1.4在建立时计入，不扩展到其他建立前行为。换设备、刷新页面、资料变化不重置周期。
- 同一行为可推进多个合格任务及多段合格关系，每段按关系和任务实例独立去重，不分摊时长；礼物子单只推进对应收礼对象的关系。基础行为成长与任务奖励分来源，奖励入当前关系现行成长账户，不新增账户或等级算法。
- **求婚戒指及升级戒指均计入日“送份礼物”和CP周“关系升温”**，仍须满足成功赠送/有效消耗与实付金币资格。按本次赠送/消耗关联的合格订单核验`actual_coin_cost > 0`；仅购买或入库未用于对应CP不计，不能仅因商品为戒指而排除。普通背包礼物、免费、运营赠送、全额券、失败订单继续不计；部分抵扣后确有金币实付且订单合格可计。BOND/CP固定成长值及戒指既有加成各按原来源入账一次，不叠加普通礼物比例；额外日+10/周+20分别去重，不把任务奖励发成两份。
- 状态为`available → in_progress → completed → credited`，另支持`expired / revoked`。自动到账唯一键为`relationship_id + cycle_id + task_code`；客户端不能依据进度条、进入目标页或点击CTA发奖。奖励回调超时先查原实例，不重复入账。
- 周期结束时未完成目标过期；已完成但奖励延迟按原实例补记。迟到的有效成功事件按原行为时间重算原周期；求婚戒指按建立时的任务有效统计时间定位，不把旧事件计进新周期。新周期重新生成8条当期任务，不把上周期完成态、按钮禁用态或计数带入新周期。
- 订单退款/拒付/订单撤销（含两类戒指）绑定原订单与原日/周实例；普通消息撤回不属于此回退：其他有效行为仍达标则保留奖励，不再达标才回退进度并生成奖励负向流水；周任务依赖的自然日计数也重算。跨周期调整不串当前周期或复建的新关系。
- pending、发送/接受失败及已解除关系不生成新正式关系任务。复建即使同对象也使用新`relationship_id`，不继承旧任务、周期计数或旧导航上下文。

#### 9.1.4 求婚戒指与升级戒指的任务归属

- **求婚戒指**：求婚发送成功先记录本申请、双方、戒指及实付订单；pending阶段不创建CP任务。对方接受、CP正式生效后，将本申请成功使用的合格戒指绑定新`relationship_id`，计入**CP建立当天**日“送份礼物”和**建立当周**“关系升温”；任务有效统计时间取`established_at`，原发送/付款时间保留供审计。若发送与接受跨日或跨周，归入接受并建立关系时的周期，不生成建立前的任务。拒绝、过期、接受失败或最终未建立CP的申请不计正式关系任务，不据此更改既有戒指退还/补偿规则。
- **升级戒指**：向当前有效CP成功赠送并确认消耗后，按赠送成功事件时间计入该CP当日/当周任务；仅打开戒指Tab、选中、支付中、买入库存或失败发送不计，事件到达晚仍绑定原成功时间的周期。
- 戒指资格由服务端关联本次赠送/消耗订单核验实付金额、成功状态及适用CP；绑定时复核订单最终有效状态，已全额退款、拒付或订单撤销不作为合格来源。不能以客户端展示价或背包/库存页面有一枚戒指作为完成凭证。普通背包礼物的排除不作为排除合格实付戒指消耗的理由；免费戒指仍按免费来源不计。
- 申请ID、订单子单/戒指消耗ID与关系ID关联去重；接受重试、消息重投、关系初始化重跑或同一赠送多次回调均只记一次。任务到账继续使用9.1.3唯一键；同单可使日+10、周+20各完成一次，不能再给已完成任务重复发奖。计入日送礼完成当天可推进周“五日有互动”，同日仍只记1天。
- 关联订单退款、拒付或订单撤销时按9.1.3重算原日/周及依赖天数；只调整原关系实例，不影响之后复建的新CP。戒指计任务不新增购买流程或改变9.4的CTA路由。

### 9.5 私聊、跟房与送礼的交互逻辑

#### 9.5.1 私聊动作

“去聊天 / 去互动 / 日任务去送礼”先校验当前关系仍有效，再按对象ID打开或创建现有私聊会话。会话被删除仍可通过用户ID重新打开，不依赖旧IM记录或旧邀请气泡；对方离线不阻断进入会话，消息/送礼权限沿用平台已有规则。拉黑、账号不可用或现有私聊权限不允许时，按已有业务提示拦截，不以“当前未在房间内”替代。

日任务“去送礼”只进入私聊页面，礼物面板沿用现有入口，不因导航自动购买或赠送。私聊没有本期关系礼物时不临时增加商品或改变礼物类型；用户可送其他合格实付礼物完成日任务。导航成功和发送按钮点击都不算任务完成，须等待消息有效发送或礼物成功送达事件。

#### 9.5.2 跟房与上麦动作

“去房间 / 去上麦”均以**当前关系对象**最新在房状态为目标；“用户不在房间”指查询到对象未在任何可跟随的房间，不指点击者自己未入房。

| 当前情况 | 行为 |
|---|---|
| 自己不在房、对象在房 | 查询通过后按既有跟房流程入对象房间，不因为自己未入房显示无房Toast |
| 自己与对象已在同一房 | 恢复/打开该房间，不重复入房；去上麦使用现有上麦入口；已经在麦不重复申请 |
| 自己在另一房、对象在房 | 复用既有切房确认与退出/入房流程；取消确认保持原房间/麦位与任务页，不强行离房或转麦 |
| 对象明确不在房 | 提示“当前未在房间内”，保持成长任务Tab、滚动和进度；不自动推荐别的房间或跳房间列表 |
| 在房查询失败/超时/状态未知 | 提示“暂时无法获取房间信息，请重试”，可重试，不把未知当作不在房，也不使用过期room_id入房 |
| 查询后对象换房/离房 | 入房前再走现有跟房校验，按最新结果处理；明确无房用指定Toast，不继续追入已关闭房间或循环自动追踪 |
| 房间关闭/满员/密码/锁房/被限制/无权限 | 复用现有入房确认与错误提示，不绕过门禁、不暴露受限房间信息；失败停留任务页，不推进任务 |
| 去上麦进入成功 | 提供/定位现有上麦入口，按当前麦位、权限、申请、麦满及麦克风授权流程执行；不静默替用户自动上麦、抢麦或解除静音 |

跟房成功只提供行为场所，不直接计时或发奖。“去上麦”也不保证对方在麦，双方真正同时在麦才计入任务。跟入非CP房不推进CP同房任务；兄弟/闺蜜/挚友在任意类型的同一房间有效陪伴均可推进同房任务，不要求主动互动。同麦仍按同一语聊房重叠时长规则，不新增CP房限制，也不因入口改动新增房间权限。

#### 9.5.3 周任务关系送礼

“关系升温—去送礼”在原提升等级页内切至关系礼物Tab，保留当前关系对象；CP展示首期适用BOND/CP商品，亲友展示适用BOND，不恢复后置的高阶商品或等级锁态。用户自行选择商品、确认支付，复用第10节订单/发放/退款服务。成功后停留关系礼物Tab并刷新余额与成长；返回成长任务Tab时重拉日/周进度及到账状态。

### 9.6 返回、刷新与异常

- 离开前保存来源关系主页、当前提升等级页、成长任务Tab、日/周分组与滚动位置；恢复优先原页面实例，不层层重复创建提升等级页。
- 从私聊或房间按既有返回方式回到任务页时，恢复成长任务Tab和滚动位置，重拉当前关系、当期8条任务及到账值。留在目标页的动作不自动跳回任务页；实时推送或重拉最终态以服务端为准。
- 任务页内切到关系礼物后，再切回成长任务，恢复原任务位置并刷新。正常从关系主页初次进入提升等级页仍默认关系礼物，不能把“返回任务页”的规则改成全局默认成长任务。
- 查看任务/私聊等页面不应额外发送离房、下麦或解静音请求；实际跨房切换按现有切房流程处理，最小化/恢复时保留原房间会话和角色。导航返回不回滚实际房间动作。
- 返回时跨日/跨周，显示新的当期任务，保留滚动在有效分组范围内，不恢复旧按钮态。关系已解除或当前对象变化时停止旧关系导航和完成逻辑，提示关系已失效并返回可用关系入口；即使同对象复建也不复用旧任务缓存。
- 同一CTA查询或跳转处理中防重复点击；明确失败恢复可点，加载/到账中不产生奖励副作用。任务达标与点击并发时刷新完成态，不重复执行送礼或自动发奖。

4. 两款礼物分别灰度，核验余额、原关系成长、任务、子单退款与旧端兼容；静态资源兜底。
5. 观察错误、投诉及补偿后扩大流量，具体地区、版本与日期由上线负责人登记。
